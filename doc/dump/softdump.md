# 波形 ROM ソフトダンプ

チップを外さずに波形 ROM 32MB を吸い出す。自作ファームウェアを本体ファーム領域だけに書き込み、
SWP30 経由で読んだデータを MIDI OUT から送出する。

## 安全性

書き換えるのは **0x040000-0x3DFFFF（本体ファームウェア）だけ**。
ダウンローダ（0x000000-0x00C001）には一切触れないので、[Drum]+[PLAY]+[VALUE+] 起動での
ダウンロードモードは常に生きており、純正アップデータ `mu2r1_uw.zip` でいつでも元に戻せる。
実機でダウンロードモードに入れることは確認済み（2026-09-05）。

## 構成要素

| ファイル | 役割 |
|---------|------|
| `tools/dump/sh2asm.py` | 最小 SH-2 アセンブラ（ラベル、自動リテラルプール、big-endian） |
| `tools/dump/make_dumper.py` | ダンパ本体を生成（エントリ 0x00040100、1,376 byte） |
| `tools/dump/make_rxtest.py` | MIDI IN の疎通だけを確かめる試験ファーム。受け取ったバイトを返す |
| `tools/dump/make_testrom.py` | MAME 検証用 romset を作る（既知パターンのダミー波形 ROM 付き） |
| `tools/dump/recv_dump.py` | PC 側の受信スクリプト（python-rtmidi）。`--monitor` で疎通確認、`--req-port` で再送要求 |
| `tools/dump/make_ydl.py` | 任意のイメージから `.ydl` を作る。公式ファイルをバイト単位で再現できることで検証済み |
| `tools/dump/build_firmware.py` | 純正ファームにトランポリンとダンパを埋め込む |
| `tools/dump/send_ydl.py` | `.ydl` を DIN の MIDI OUT から送る（純正 Upgrade.exe の代替、USB ドライバ不要） |

## ダンパの動作

1. SH7043 の SCI0 を 31250bps に設定（SMR=0, BRR=27, SCR=TE|RE）。
   MIDI OUT は SCI0 の TX、MIDI IN A は同じ SCI0 の RX なので全二重で使える
2. SWP30 を起動時初期化する（後述）
3. SWP30 の wave direct access で波形 ROM を 32bit ずつ読む
   - 0x80011C / 0x80011E にアドレス（32bit ワード単位、0x000000-0x7FFFFF）
   - 0x80021C に 0x8000 を書いてトリガ
   - 0x80029C / 0x80029E からデータを読む
4. 128 ワードごとに SysEx 1 個で送出。全部送ったら先頭から繰り返す

SysEx 形式（1 個 654 byte。Windows の MIDI ドライバは 1024 byte を超えると分割するので
その範囲に収めてある）:

```
F0 43 7D 'M' 'U' 'W' 'D' <ブロック番号 4x7bit> <128 ワード x 5x7bit> <加算和 2x7bit> F7
```

1 ワードは 32bit を上位から 4,7,7,7,7 bit の 5 個に分割する。繰り返し送出するので、
取りこぼしたブロックは次の周回で埋まる（`recv_dump.py` が管理する）。

加算和はブロック番号の 4 バイトとペイロードの 640 バイトを単純に足した下位 14bit。
受信側は合わないブロックを捨てるので、化けたデータが `.part` に混ざらない。

## 再送要求（PC -> MU2000）

一巡は約 3.8 時間かかる。取りこぼしを次の周回まで待たずに済むよう、PC 側から
「このブロックを今すぐ送れ」と言えるようにしてある。

```
F0 43 7D <ブロック番号 4x7bit> F7
```

ダンパは送出中のブロックを送り終えた時点でそのブロックへ飛び、そこから順送りを続ける。
`recv_dump.py --req-port` が、穴が残っているのに既取得のブロックが続いたときや
1.5 秒無音になったときに、次に欠けているブロックを要求する。

実装上の注意が 3 つある。どれも MAME で実際に踏んだ。

- **ポーリングは 1 バイト送出待ちのスピンループの中で行う。** MIDI のバイト間隔は 320us、
  SCI の受信バッファは 1 バイトしかない。ブロックの切れ目でしか見ないと必ず取りこぼす
- **受信エラー（ORER/FER/PER）は RDRF が立っていなくても毎回落とす。** SH7043 の SCI は
  エラーが立ったままだと受信を再開しない。RDRF が立っているときだけ SSR を触る作りにすると、
  一度エラーが出た時点で受信が永久に止まる
- **成立した要求は状態機械とは別のレジスタ（r15）に持つ。** SysEx の状態機械の中に置くと、
  次に届いた `F0` が保留中の要求を上書きしてしまう

受信は既定で SCI0（MIDI IN A）。`--rx-sci 1` で SCI1（MIDI IN B）に変えられる。
状態機械が 1 組しかないので両方を同時には見ない（同じ要求が 2 系統から入ると壊れる）。

ピン機能（PFC）と PA21（MIDI A の前面/背面切替）はダウンローダが起動時に設定済みで、
ダンパはそれを引き継ぐ。念のため PA21 だけはダウンローダと同じ値（出力・1）を書き直している。

## SWP30 レジスタ番地の求め方

レジスタ番地 = SWP30 ベース + ((レジスタ番号 << 6) | チャンネル) << 1。
コントロールレジスタはチャンネル 14 / 15 に現れる。MU2000 のマスター SWP30 は CPU の 0x800000。
全レジスタに自分のオフセット値を書き込むプローブを MAME で流して実測確認済み。

## MAME での検証結果（2026-09-05）

既知パターン `wave_word[i] = i | 0xE0000000` のダミー波形 ROM を用意し、
MAME → loopMIDI → `recv_dump.py` で受信した。

| 項目 | 結果 |
|------|------|
| 波形 ROM 読み出しアドレス | 0,1,2,3... と正しく進む |
| 受信ブロック | 32/32（100%） |
| ワード不一致 | 0 |
| 速度 | 約 4.8 ブロック/秒 = 約 615 ワード/秒 |

全 32MB の所要時間は約 3.8 時間（MIDI 31250bps が律速）。

再現手順:

```bash
python tools/dump/make_dumper.py --rom-words 0x1000 -o build/dumper_test.bin
python tools/dump/make_testrom.py
python tools/dump/recv_dump.py --port "loopMIDI" --out build/recv_test --words 0x1000 --timeout 8 &
mame/mame.exe mu2000 -rompath build/recv_rom -bios v200 -window -midiout "loopMIDI Port" -str 25
```

## .ydl 生成器

`tools/dump/make_ydl.py` は純正 `v200u22k.ydl` を雛形にして、コマンド列・デルタタイム・
メッセージ構造をそのまま流用し、**中身のデータとチェックサムだけ差し替える**。
未解析のコマンド（0x00 のパラメータ、転送完了の 0x0E）を推測せずに済む。

チェックサムは 2 種類あり、どちらも公式ファイルから逆算して確定した。

| 対象 | 計算 |
|------|------|
| メッセージ単位 | コマンドバイトからチェックサム直前までの総和が 128 の倍数になる値 |
| セクタ単位 (cmd 03) | 書き込み範囲のデータバイトの 28bit 単純加算を 4×7bit で送る |

検証: 純正イメージを入れると出力が公式 `.ydl` と **4,583,144 バイト全て一致**する。

```bash
python tools/dump/make_ydl.py --image roms/mu2000_flash.bin --verify
```

## 書き込むファームウェアの構成

`tools/dump/build_firmware.py` が純正ファームを土台に次を埋め込む。

| 番地 | 内容 |
|------|------|
| 0x040100 | 0x041000 へのジャンプ（12 byte）。ダウンローダが JSR する入口 |
| 0x041000 | ダンパ本体（1,376 byte） |

0x040204 以降の割り込みベクタスタブは温存する（ダンパは割り込みを全マスクするので実際には使わない）。

## 双方向版の検証（2026-09-06）

loopMIDI を MAME の `-midiin1` と `-midiout` の両方に割り当てて動かした
（MAME 0.289 では MIDI ポートはイメージデバイス扱いで、オプション名は `-midiin1` /
`-midiin2` / `-midiout`。`-midiin` は無い）。

| 項目 | 結果 |
|------|------|
| 診断メッセージ | 期待どおり（アドレス 1 の読み出し値 0xE0000001） |
| 加算和 | 373 ブロック連続で NG 0 |
| データ一致 | 373/373 |
| 再送要求 | ブロック 3 の後に 5000 を要求 → `0,1,2,3,4,5,5000,5001` と飛んだ |

要求から実際に飛ぶまで 2 ブロックかかっているのは、この構成では MAME の出力が
自分の MIDI IN にも返っていて、その分だけ要求の到着が遅れるため。実機では起こらない。

再現手順:

```bash
python tools/dump/make_dumper.py -o build/dumper_v3.bin
python tools/dump/build_firmware.py -o build/firmware_v3.bin
python tools/dump/make_testrom.py --firmware build/firmware_v3.bin --out build/v3_rom
python build/v3mon.py &
mame/mame.exe mu2000 -rompath build/v3_rom -bios v200 -window -skip_gameinfo -midiin1 "loopMIDI Port" -midiout "loopMIDI Port" -seconds_to_run 85
```

## 実機での結果（2026-09-05）

USB 経由で純正 Upgrade.exe から書き込み、電源投入と同時にダンプが始まることを確認した。

| 項目 | 結果 |
|------|------|
| セクタ書き込み | 全て成功 |
| 転送完了チェックサム | 初回は NG（コマンド 0x0E の値が未解析だったため）。起動には影響しなかった |
| 起動後 | 電源投入直後から SysEx が流れ始める |
| 受信データ | ヘッダ・ブロック番号・長さすべて設計どおり |

コマンド 0x0E は 4MB 全体のバイト総和の下位 16bit と判明し、`tools/dump/make_ydl.py` で
自動計算するようにした（[doc/dump/updater-protocol.md](updater-protocol.md) 参照）。

## 吸い出し完了（2026-09-06）

v3（SWP30 初期化 + 双方向）を USB 経由で書き込み、MIDI で 32MB を吸い出した。

| 項目 | 結果 |
|------|------|
| 取得ブロック | 65,536 / 65,536（一周で完走） |
| 加算和 NG | 0 |
| 再送要求 | 0 回 |
| 速度 | 4.8 ブロック/秒 → 3.8 時間 |
| 照合 | 波形 ROM 4 本すべて MAME 登録の SHA1 と一致 |

```
xv364a0.ic49  e7098246b33c3cf22ed8cc15ed6383f8a06d17e9
xv365a0.ic50  d45a2e85859e05046f3ede8317a9bb0b88898116
xw848a0.ic53  9e8b55c2cbac3f69cc0b17aeaf02053145bfaeda
xw849a0.ic54  7670d672e24d6388fa92799175f35869a140c451
```

`roms/mu2000.zip` に本物の波形 ROM 入り romset ができている。

加算和 NG も再送要求も 0 だったので、実機の MIDI 経路では 4,300 万バイトを
1 バイトも落とさずに送れたことになる。再送要求の機構は今回は出番が無かったが、
取りこぼしがあった場合に一周（3.8 時間）待たずに済む保険として働く。

### 実機と MAME の違い

診断メッセージで、SWP30 のアドレス・サイズレジスタが実機では読み返すと 0 になった
（MAME では書いた値がそのまま読める）。実機のコントロールレジスタは書き込み専用らしい。
データレジスタは読めるのでダンプには影響しない。

### LCD について

ダンパは LCD を操作しないので、起動後の表示は初期化されないままの意味のないパターンになる。
故障ではない。パネル操作にも反応しない。停止するには電源を切る。

## 実機で必要なもの

- MU2000 の MIDI OUT から PC の MIDI IN への 5 ピンケーブル（Babyface の MIDI IN が使える）
- PC の MIDI OUT から MU2000 の MIDI IN A への 5 ピンケーブル（再送要求用。無くても動く）
- USB ケーブル（ファームウェア書き込み用。Yamaha USB-MIDI ドライバが必要）
- ダンプ中は電源を切らないこと。約 3.8 時間
